# Telegram Mini App тренера

Тренерский экран доступен по `/tma/trainer` (также с завершающим `/`). Клиентский Mini App на `/tma` сохранён. Кнопка «Открыть расписание тренера» добавлена в меню бота для тренеров и администраторов. Новые зависимости и миграции БД не нужны.

## Вход и доступ

`POST /api/tma/auth` принимает только `{ initData: string }`. Используется существующая проверка Telegram HMAC, допускающая подписанные данные не старше часа и рассинхронизацию часов до 30 секунд. Подмена, повторяющиеся ключи и невалидный Telegram user отклоняются. Алгоритм: `secret = HMAC-SHA256(key="WebAppData", data=botToken)`, затем HMAC строки проверки. Это алгоритм [Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), отличающийся от обычного SHA256 токена бота.

Идентификатор ищется в `User.telegramUserId`; пользователь должен иметь активную карточку `User.trainerId`, включённый CRM-доступ и активный профиль сотрудника (если он есть). При отсутствии пользователя ответ `{ authenticated: false, reason: "NOT_LINKED" }`. Автоматическое создание или связывание карточек при входе не выполняется. Для привязки используется существующая CRM-форма Telegram в карточке сотрудника/пользователя.

Ответ успешного входа: `{ authenticated: true, access_token, trainer: { trainerId, name }, accessLevel }`. JWT живёт один час, содержит `aud=trainer-tma`, `tokenType=trainer-tma` и версию отзыва сессий. Токен хранится только в памяти TMA, передаётся в `Authorization: Bearer …`, не использует CRM cookies и не открывает CRM API. Каждая операция заново проверяет актуальную привязку Telegram, активность профилей, версию токенов и модуль SCHEDULE. READ_ONLY разрешает просмотр, HIDDEN блокирует доступ. Изменение статуса и замена лошади повторно проверяют Telegram-привязку, принадлежность и права внутри транзакции.

## API

* `GET /api/tma/schedule?date=YYYY-MM-DD`: занятия только текущей карточки тренера, московские полуоткрытые границы суток, сортировка startTime/id. Поля: id, startTime, endTime, status, serviceName, clientName, horseId, horseName, notes, participants. Отменённые занятия сохраняются в выдаче. `notes` содержит сохранённую причину отмены/неявки. Для группы participants содержит bookingId, имя всадника и назначенную лошадь; общий horseId равен null. Самостоятельные бронирования без Lesson не входят в этот API занятий.
* `PATCH /api/tma/lessons/:id/status`: `{ status: "COMPLETED" | "CANCELLED" | "NO_SHOW", reason?: string }`. Для отмены/неявки обязательна непустая причина до 300 символов. Статус относится ко всему занятию, включая группу. Используется LessonsService: списания абонемента, отмена, аудит и уведомления сохраняют существующие транзакционные правила. Тренер меняет свои занятия, ADMIN может изменить чужое занятие. Для отмены с оплатой требуется решение о возврате через существующий CRM-процесс администратора; TMA не передаёт refund и не принимает решение о сохранении денег.
* `PATCH /api/tma/lessons/:id/horse`: `{ horseId, bookingId? }`. Для группы bookingId обязателен и должен принадлежать этому занятию. Для одного участника определяется сервером. Используется BookingsService.replaceHorse с аудитом: проверяются здоровье, нагрузка в минутах, отдых, вес всадника, конфликты ресурсов и дополнительные права замены лошади. По существующему контракту замена доступна до начала запланированного занятия.
* `GET /api/tma/horses`: `{ id, name }[]`, только active/HEALTHY, без isUnavailable; фактическая пригодность для конкретного занятия повторно проверяется при сохранении.

Все идентификаторы проверяются UUID pipes/DTO и на фронтенде перед мутацией. Данные и ответы авторизации не кэшируются. Тела запросов не позволяют указать trainerId или пользователя.

## Интерфейс и развёртывание

`frontend/src/RootRoutes.tsx` лениво выбирает тренерский экран до монтирования CRM: sidebar, шапка и CRM-провайдер авторизации не запускаются. `docker/Caddyfile` отдельно направляет `/tma/trainer[/]` на frontend index.html; клиентский `/tma/*` продолжает обслуживать прежнюю сборку. Исключение для Telegram iframe и SDK ограничено Mini App маршрутами. Стандартный deploy-native собирает frontend, затем клиентский tma; новые артефакты тренера находятся в frontend/dist/assets и не удаляются сборкой tma.

Нужны существующие `JWT_SECRET`, `TELEGRAM_BOT_TOKEN` и публичный HTTPS-хост CRM. После выкладки требуется перезапуск backend и применение конфигурации Caddy. Публикация и подключение к реальному Telegram в рамках локальной проверки не выполняются.

Селектор недели загружает семь независимых дневных ответов, показывает известные счётчики и отдельную ошибку текущего дня. Старые запросы отменяются при переключении недели/повторе. Bottom Sheet использует Ant Design Drawer/Select с клавиатурой и невиртуализированными опциями. Ошибка сохранения сохраняет выбор и причину, повторная отправка блокируется. Инициализация вызывает ready/expand; тема обновляется по themeChanged, отступы учитывают safe area. Сессия, ошибки, пустой день и повтор загрузки имеют отдельные состояния.

## Проверки

* Backend: `npm run typecheck`, `npm run lint`, `npm run build`, `npm test`; новые HTTP и mock-тесты `backend/test/trainer-tma.test.cjs`.
* Frontend: `npm run typecheck`, `npm run lint`, `npm run build`, `npm test`.
* Браузер: `npx playwright test --config=playwright.tma.config.ts` из frontend; моки Telegram SDK/API, реальные React/Ant Design и браузер Edge. Проверяются мобильная ширина, московское время, изоляция CRM, статусы, причины, конфликт замены, повтор, клавиатура, тёмная тема, READ_ONLY, отсутствие привязки и истечение сессии.
* Статический premium-аудит сохраняется в `test-results/tma-premium-audit.json`; существующие нарушения других экранов не входят в эту задачу.

Реальные Telegram iOS/Android, bot token и серверная БД требуют проверки после развёртывания; mock E2E не заменяет эту проверку.
