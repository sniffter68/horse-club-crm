# Продажа абонементов

`POST /api/memberships`, роли ADMIN/MANAGER. Клиент, услуга (или базовая цена / существующий тариф), количество занятий, итоговая сумма и способ оплаты проверяются сервером. Обязательны `totalPrice >= 0` с точностью до копеек и `paymentMethod: CASH | CARD`. Количество можно получить из тарифа; дату окончания — из его срока. Услуги с `allowMembership=false` продавать по абонементу нельзя.

Цена услуги и её название сохраняются на момент продажи; дальнейшее изменение прайса не меняет оформленный абонемент. `pricePerLesson` и `totalPrice` — Decimal(12,2). Изменяемая итоговая сумма позволяет предоставить персональную скидку. Если выбран тариф, он заполняет количество и срок, а рекомендуемая стоимость в форме определяется услугой.

Одна Serializable-транзакция Prisma сохраняет:

- Membership с услугой, ценами, способом оплаты, продавцом из JWT и обоими представлениями баланса занятий;
- CREDIT MembershipOp и связанную каноническую запись начисления занятий;
- при включённой кассе — PAID Payment с клиентом, услугой, абонементом, кассиром, активной сменой и `serviceType=MEMBERSHIP`, затем денежную LedgerTransaction со связью `cashDeskPaymentId`.

В этой модели нет отдельного CashTransaction: приход определяется оплаченной записью Payment, а категория — serviceType. Денежная запись purchase и начисление занятий разделены; история клиента показывает рубли и занятия в соответствующих единицах. Кассовые итоги автоматически включают PAID-платёж. Нулевая сумма разрешена и сохраняется как оплаченная операция.

Запись журнала занятий создаёт PostgreSQL-триггер `MembershipOp_project_ledger` из миграции `20261009010000_booking_lifecycle_ledger`. Сервис не вставляет эту проекцию повторно: уникальный `sourceMembershipOpId` связывает её с CREDIT. Повторная ручная вставка вызывала P2002 и откат продажи; регрессия воспроизводится в `membership-sale.postgres.test.cjs`.

Глобальный флаг CASHBOX и права проверяются внутри транзакции. При включённой кассе требуется FULL; ADMIN всегда FULL. При отключённой кассе создаются абонемент и журнал занятий без платежа и денежного журнала. Поэтому безусловный `@RequireModule('CASHBOX')` к продаже неприменим: он запретил бы явно разрешённое оформление при отключённом модуле. JWT и RolesGuard защищают контроллер, условную финансовую проверку выполняет MembershipsService.

Ошибка сохранения абонемента, начисления занятий, платежа или денежного журнала откатывает всё оформление. `requestId` (UUID) обеспечивает безопасный повтор: advisory lock, уникальный ключ и отпечаток входных данных предотвращают повторную продажу. Другие данные с тем же ключом дают 409. Ошибки сериализации повторяются ограниченное число раз.

Форма использует общий EntryOverlay в режиме drawer, ClientSelectWithCreate, Ant Form/Select/InputNumber/Segmented/DatePicker и уведомления App. Срок заканчивается в 23:59 выбранного дня по Москве. Во время запроса повторная отправка и закрытие блокируются. Неопределённый исход сохраняет исходный запрос и его ключ для повтора. После успеха обновляются запросы клиентов/абонементов/платежей и отправляется существующее событие `cash-desk-paid`, которое обновляет кассу и дашборд.

Известные конфликты Prisma возвращаются как 409, отсутствующие таблицы/колонки — как 503 с кодом `MEMBERSHIP_SCHEMA_OUTDATED`; подтверждённый откат помечается `details.rollbackConfirmed=true`. В этом случае форма сохраняет введённые данные, разблокирует поля и создаёт новый ключ при следующей отправке. При сетевой ошибке или неопределённом 5xx исходный ключ сохраняется. Генерировать новый ключ после потери ответа небезопасно: предыдущий запрос мог уже завершиться оплатой. В логах backend событие `membership_sale_failed` содержит этап, номер попытки, requestId, actorId/clientId, код/метаданные Prisma и стек; полный DTO в лог не передаётся.

Перед запуском новой версии на сервере применить `20261020120000_membership_sale` командой `npx prisma migrate deploy` в backend и сгенерировать клиент. Миграция добавляет nullable-поля для старых абонементов и не создаёт исторические платежи. Backend и frontend следует обновлять вместе: API продажи теперь требует итоговую сумму и способ оплаты.

Проверки: `backend/test/membership-sale.test.cjs`, `backend/test/client-membership-display.test.cjs`, `frontend/e2e/clients-memberships.spec.ts`, регрессия `frontend/e2e/cash-desk.spec.ts`. Браузерные сценарии используют mock API. Интеграционная проверка: `npm run test:memberships:postgres` из backend; при другом локальном порте задайте `MEMBERSHIP_TEST_PORT`. Runner применяет все миграции только в новой изолированной локальной схеме, проверяет реальный триггер, CASH/CARD, конкуренцию и откат и затем удаляет тестовую схему. Рабочая схема базы не изменяется. Состояние миграций на production проверяется отдельно при выпуске.
