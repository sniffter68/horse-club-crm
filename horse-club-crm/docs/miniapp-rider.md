# Кабинет всадника в Telegram Mini App

Реализован 21.11.2026. Клиентский интерфейс — отдельный пакет `tma/`, вход и режимы персонала — `frontend/src/tma/`. Схема Prisma не менялась, миграция не нужна.

## Вход и границы доступа

`POST /api/tma/bootstrap` и его алиас `/api/tma/auth/telegram` принимают `{initData}`. Существующая HMAC-SHA256-проверка отклоняет подделку, дубликаты параметров и подпись старше часа. Приоритет: User → устаревшая связь Trainer с User → Client.telegramUserId (String). Неактивный сотрудник получает 403, а не клиентскую сессию. Сотрудник без Trainer получает STAFF с правами своей реальной CRM-роли; TRAINER и ADMIN сохраняют свои экраны.

Привязанный клиент получает токен с `tokenType=client-tma`, `aud=client-tma`, сроком 1 час. Он хранится только в памяти. На каждом клиентском запросе проверяются подпись токена, включённость SCHEDULE, существование активного клиента и сохранность привязки Telegram. Токен клиента не принимается авторизацией CRM или тренера. Для первоначального оформления нового клиента сохраняется существующий протокол `Authorization: tma <initData>`.

Интерфейс ожидает SDK/initData, показывает загрузку и сразу открывает «Кабинет всадника». Прямой вход сотрудника на клиентский маршрут возвращает его в ролевой шлюз. Вне Telegram показывается инструкция открыть приложение через бота.

## Подтверждение телефона

Вручную введённый номер больше не даёт доступ к существующей карточке CRM. Кнопка «Привязать по телефону» вызывает `POST /api/tma/client/request-contact`: бот отправляет клавиатуру Telegram `request_contact`. Пользователь делится своим контактом в личном чате бота, затем нажимает «Проверить привязку» в Mini App.

Обработчик Bot API проверяет `contact.user_id === from.id`, нормализует +7/8 и находит существующий Client.phone. Привязка и аудит выполняются в Serializable-транзакции; чужая действующая привязка и архивный клиент отклоняются. Временная карточка не удаляется, её история сохраняется. Контакт, переданный JSON-запросом из браузера, не считается доказательством владения телефоном. Сбой или отсутствие карточки требуют помощи администратора.

## Клиентский API

Все идентификаторы проверяются DTO/ParseUUIDPipe; clientId определяется сервером.

| Маршрут | Результат |
|---|---|
| `GET /api/tma/client/overview` | Свой профиль, абонемент или null, ближайшие записи с услугой, тренером, лошадью, canConfirm/canCancel |
| `POST /api/tma/client/lessons/:id/confirm` | Подтверждение собственной предстоящей записи, аудит |
| `POST /api/tma/client/lessons/:id/cancel` | Отмена своей записи, возврат ранее списанного посещения, аудит и уведомление администратора |
| `GET /api/tma/client/booking/slots?date=YYYY-MM-DD&serviceId=UUID&trainerId=UUID` | Доступность услуги, тренера и хотя бы одной подходящей клубной лошади |
| `POST /api/tma/client/booking` | Создание SCHEDULED; тело как у существующего `/api/tma/bookings` |

Пути `/slots` и `/bookings` сохранены как алиасы. Идентификатор действия может быть ID Booking либо ID Lesson, обязательно с проверкой clientId. Повтор подтверждения/отмены идемпотентен.

В Prisma нет CONFIRMED у LessonStatus: подтверждение конкретного всадника хранится в существующем `Booking.clientConfirmed`; API отдаёт `clientStatus=CONFIRMED`. Это не переводит всё групповое занятие в новый статус. Новая enum-миграция не требуется.

## Запись, отмена и финансы

Дата и время — Europe/Moscow, горизонт записи — 30 дней. Учитываются часы клуба и смена тренера на выбранную дату (при отсутствии индивидуальной смены используется расписание клуба). Существующие BookingRulesService и LessonsService проверяют ёмкость тренера, занятость клиента/лошади, здоровье, допустимый вес, отдых и нагрузку лошади в минутах. Слоты проверяются без резервирования; запись повторяет проверки с блокировками ресурсов внутри Serializable-транзакции. При исчерпании конфликтных повторов возвращается 409. Параллельные всадники у одного тренера разрешены до его настроенного maxParallelLessons; одна лошадь не может быть занята дважды. requestId защищён существующим уникальным индексом.

Отмена выполняется в той же транзакции, что возврат посещения и AuditLog (`CashAuditLog` проекта). Журнал MembershipOp сохраняет DEBIT/REFUND и не увеличивает баланс без фактического списания. Поддержан старый owner-DEBIT без attendeeClientId. Для самостоятельной записи без Lesson используется существующий LedgerTransaction и возврат remainingUnits. Синхронизацию целочисленного остатка обеспечивает существующий триггер БД. В группе отменяется только текущий участник; остальные сохраняют занятие. Отменённые участники исключены из ресурсных расчётов и последующего списания при завершении группы. Последняя отмена переводит Lesson в CANCELLED. Денежные платежи сохраняются; денежный возврат остаётся административной операцией CRM.

Создание, подтверждение и отмена записывают аудит с clientId и временем БД, уведомления администраторам добавляются в существующий outbox в той же транзакции.

## Интерфейс и проверка

Единая тёмная палитра Mini App, верхний отступ не меньше 20px и значений Telegram safeAreaInset/contentSafeAreaInset, tabular-nums. Общий ClientDashboardView обслуживает кабинет и историю записей, исключая расхождение действий. Ошибки сохраняют выбор и допускают повтор, повторная отправка блокируется синхронно через ref. Отмена требует отдельного подтверждения.

Backend: `backend/test/client-miniapp.test.cjs`, `telegram-bot.test.cjs`, `trainer-tma.test.cjs`, `tma-phone-link.test.cjs`; браузер: `tma/e2e/rider.spec.ts`, `tma/e2e/booking.spec.ts`, `frontend/e2e/trainer-tma.spec.ts`. Моки покрывают клиентский автологин без сотрудника, области токенов, отзыв привязки, собственность данных, возврат посещения, аудит/откат и конкурирующие запросы к слоту. Сценарии с реальным PostgreSQL требуют отдельной тестовой базы; мок транзакции не доказывает поведение реальных блокировок БД.
