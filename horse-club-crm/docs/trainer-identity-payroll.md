# Единая карточка тренера и зарплатные ведомости

Аудит и исправления от 19.11.2026.

## Найденный разрыв

- `User.trainerId` уже был nullable и UNIQUE: нужная связь 1:1 существовала, дополнительная модель тренера не нужна.
- `Lesson.trainerId` уже указывал на справочник `Trainer`.
- `TrainerPayout` требовал `StaffProfile`, который требовал `User`. Генератор выбирал только активные профили сотрудников с привязанной учёткой. Тренеры из расписания без профиля не попадали в аванс/зарплату.
- Создание сотрудника с ролью TRAINER создавало новую карточку тренера, если у аккаунта ещё не было `trainerId`, без поиска существующей карточки.
- `WorkspaceService.trainerBoard` уже правильно выделял свои занятия по `actor.trainerId`, возвращал всех активных тренеров и скрывал данные чужих клиентов. `/schedule` также фильтрует справочник по `isActive`, независимо от логина. Изменения этой логики не потребовались; добавлены проверки одинаковых имён и тренеров без логинов.

## Итоговый контракт

`Trainer → Lesson / TrainerPayout` — основная идентичность тренера. `User.trainerId` предоставляет опциональный вход в CRM; `StaffProfile` нужен для общих кадровых функций и смен, а не для выдачи тренерской зарплаты.

Новая ведомость хранит `trainerId`, а `staffId` больше не обязателен. Исторический `staffId` сохраняется. Генератор выбирает активных тренеров с неудалёнными COMPLETED-занятиями в московских границах выбранного периода. Наличие аккаунта, `crmAccess`, профиля сотрудника или Booking не является условием начисления. Каждый Lesson считается один раз, независимо от числа участников; база — актуальная `Service.price`, доля — Decimal 30% с округлением до копеек по каждому занятию. Скидка и фактическая оплата клиента не влияют на эту долю.

Уникальность `(trainerId, type, periodStart, periodEnd)` исключает повторное создание одного расчёта. Аванс вычитается из итоговой зарплаты только после выплаты. Проверки и SQL-триггеры блокируют пересечение с оплаченными кадровыми расчётами и повторные выплаты, включая случай, когда StaffProfile добавлен после тренерской выплаты. Закрытый месяц проверяется даже при отсутствии подходящих занятий. Выплата и расход SALARY основной кассы, изменение статуса и аудит выполняются в одной Serializable-транзакции с повторами при конфликте сериализации. SQL-представление `v_cashbox_balances` не менялось.

Общий кадровый расчёт `PayrollCalculation` сохраняется для смен, ставок и исторических выплат; он не является источником нового аванса/зарплаты тренеров. Привязку пользователя с оплаченным кадровым расчётом нельзя переназначить или снять без отдельной сверки, поскольку старые начисления определяют тренера через эту связь.

## Доступ в CRM

`POST /api/trainers/:id/account`, только ADMIN с модулем STAFF_PAYROLL:

- `{ email, password }` создаёт User с ролью TRAINER на существующую карточку;
- для уже привязанной отключённой учётки обновляет email/пароль и включает доступ с сохранением User.id;
- `{ userId }` привязывает свободного пользователя с ролью TRAINER, сохраняя его текущий статус доступа;
- смена чужой привязки, повторное создание активного логина и привязка иной роли отклоняются;
- пароль хешируется bcrypt, минимум 12 символов, максимум 72 байта UTF-8; хеш не возвращается;
- изменение отзывает старые сессии через tokenVersion и пишет TRAINER_ACCOUNT_LINKED без пароля в аудит.

Карточка и список тренеров показывают статус доступа. Администратор выдаёт или привязывает логин в общей шторке StableEntryModal/EntryOverlay. Повторный submit блокируется; ошибка сохраняет введённые значения. Успех обновляет кэш trainers/users/staff и оставляет пользователя в карточке. Настройки отключённой привязанной учётки можно включить той же кнопкой выдачи доступа.

В форме сотрудника можно явно выбрать существующего тренера. Без явного выбора сервер переиспользует единственное совпадение имени/телефона; несколько совпадений или занятая карточка дают 409. Если совпадений нет, сохраняется прежняя возможность создать нового тренера.

## Миграция и выкладка

Применить `20261119120000_trainer_identity_payroll` на сервере через `prisma migrate deploy` вместе с новой версией backend/frontend. На рабочей БД миграция в рамках этой задачи не запускалась.

Миграция добавляет связь, делает старый staffId опциональным и переносит идентичность существующих ведомостей через StaffProfile → User → Trainer. Автоматическая привязка свободных TRAINER-аккаунтов использует нормализованное имя и телефон StaffProfile. Совпадение должно быть единственным с обеих сторон, тренер не должен быть уже занят другой учёткой. Email в Trainer отсутствует, поэтому сопоставление по email невозможно без дополнительных данных; из адреса почты имя не угадывается. Существующие привязки сохраняются.

Оплаченные ведомости получают только trainerId: суммы, детализация, createdAt/updatedAt, расходы и статусы не переписываются. Business-триггер этой таблицы отключается только на время backfill внутри транзакции с блокировками и включается до commit. Другие финансовые защиты действуют. Данные не удаляются, дубли тренеров автоматически не объединяются.

Неоднозначные исторические ведомости сохраняются с trainerId=NULL и отображаются с прежним ФИО. Мутации таких ведомостей и генерация новых расчётов после привязки их пользователя требуют отдельной сверки: система отклоняет операцию, а не создаёт второй расчёт. Контроль после выкладки:

```sql
SELECT p.id, p."staffId", p.status, s."fullName", u.email
FROM "TrainerPayout" p
LEFT JOIN "StaffProfile" s ON s.id = p."staffId"
LEFT JOIN "User" u ON u.id = s."userId"
WHERE p."trainerId" IS NULL;

SELECT u.id, u.email, s."fullName", s.phone
FROM "User" u LEFT JOIN "StaffProfile" s ON s."userId" = u.id
WHERE u.role = 'TRAINER' AND u."trainerId" IS NULL;
```

Для таких записей требуется проверка владельца и отдельная аудируемая миграция идентичности. Откат приложения после появления новых ведомостей без staffId требует совместимой версии: старый backend/frontend ожидает обязательный профиль сотрудника. Удалять новые связи или ведомости при откате нельзя.
