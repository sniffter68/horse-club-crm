# Ветеринария

Раздел `/vet` и вкладка «Здоровье и ковка» используют новый журнал выполненных процедур `VetRecord`. Прежний `VetEvent` остаётся календарём назначений: его история, запланированные процедуры и совместимость API сохраняются. Ветпаспорт содержит оба источника и старый `HorseHealthLog`; авторы старых процедур не выдумываются.

## API

- `GET /api/vet/records`: `horseId`, `type`, `from`, `to`, `offset` (0), `limit` (20, максимум 100). Пустые query-параметры игнорируются. Даты без смещения интерпретируются в Москве; конечная дата без времени включает весь день.
- `POST /api/vet/records`: выполненная процедура, автор берётся из сессии. Типы: `VACCINATION`, `DEWORMING`, `BLOOD_TEST`, `FARRIER`, `EXAMINATION`, `TREATMENT`, `DENTAL`.
- `POST /api/vet/records/batch`: вместо `horseId` — `horseIds`, 1–100 уникальных UUID; вакцинация или дегельминтизация. Все лошади проверяются и блокируются до записи; операция атомарна.
- `PATCH /api/vet/records/:id`, `DELETE /api/vet/records/:id`.
- `GET /api/vet/upcoming`: прежние `data`/`total` календаря плюс `overdue`, `next14Days`, `next30Days`, `thisMonth`, `restrictedHorses`. `GET /api/vet/summary` возвращает только новую сводку.
- `PATCH /api/vet/horses/:id/health-status`: `healthStatus`, необязательный `quarantineUntil`.
- `GET /api/vet/horses/:id/passport`: полный анамнез без пагинации; интерфейс поддерживает JSON и печать А4 / сохранение PDF средствами браузера.

ADMIN/MANAGER создают и редактируют новые записи и меняют здоровье. Удаление — только ADMIN. TRAINER читает журнал и паспорт при `healthRead`, но не получает права записи даже при включённом `healthWrite`. Прежний календарь сохраняет ранее настроенную политику доступа. Ссылка на скан принимает только HTTP(S). Стоимость хранится как Decimal; запись не создаёт автоматически финансового расхода в кассе.

## Сроки и здоровье

Рабочие интервалы по умолчанию: дегельминтизация 90 дней, расчистка 45, кровь 180, вакцинация/стоматология 365. Это редактируемые организационные подсказки, а не медицинские назначения. Для осмотра/лечения автоматического интервала нет. Отсутствующий `nextDueDate` включает расчёт; явный `null` отключает напоминание. Изменение типа/даты через PATCH без срока пересчитывает срок; изменение только заметок его сохраняет.

Просрочка определяется по календарной дате Europe/Moscow: процедура со сроком сегодня ещё не просрочена. Сводка использует последнюю запись для сочетания лошадь/тип/название, чтобы повторная выполненная процедура закрывала прежний срок. Названия разных вакцин и исследований сохраняют независимые сроки. Блоки 14 и 30 дней пересекаются; месячный блок относится к календарному месяцу. Старые назначения отображаются в отдельном календаре.

`TREATMENT`, `QUARANTINE`, `RETIRED` блокируют новые назначения с HTTP 400 в общей проверке бронирований и проверке нагрузки legacy-занятий. Проверка не снимается автоматически после `quarantineUntil`. Изменение здоровья блокирует строку лошади в serializable-транзакции и синхронизирует прежние `status`/`isUnavailable`, поэтому существующие предупреждения расписания и подбор альтернатив продолжают работать. Уже созданные занятия не отменяются и оплаты не меняются: администратор заменяет лошадь через существующий список предстоящих занятий.

## Развёртывание и проверки

Перед запуском backend применить `20261018120000_vet_records` и пересоздать Prisma Client:

```powershell
cd backend
npx.cmd prisma migrate deploy
npx.cmd prisma generate
npm.cmd run build
```

Миграция добавляет таблицу и поля, переносит существующие sick/quarantine в статус здоровья и сохраняет старую историю. Нужна доступная PostgreSQL. Проверки: `backend/test/vet-records.test.cjs`, `backend/test/booking-rules.test.cjs`, `frontend/e2e/vet-records.spec.ts`, регрессия `frontend/e2e/vet-log.spec.ts`.

PostgreSQL-интеграция: `backend/test/vet-records.postgres.test.cjs` запускается существующим `node test/run-stall-postgres.cjs` в одноразовой локальной базе. Live Playwright: `frontend/e2e/vet-records.live.spec.ts`, переменные `CRM_VET_ADMIN_EMAIL`, `CRM_VET_ADMIN_PASSWORD`, `CRM_VET_HORSE_ID` и локальный `CRM_TEST_BASE_URL`. Использовать здоровую тестовую лошадь; тест удаляет созданную запись и возвращает ей здоровье после проверки. Без переменных live-тест пропускается.
