# Исправление ошибки продажи абонемента — 20.10.2026

## Причина и исправление

Миграция `20261009010000_booking_lifecycle_ledger` установила PostgreSQL-триггер `MembershipOp_project_ledger`: после создания CREDIT он автоматически вставляет LedgerTransaction с уникальным `sourceMembershipOpId`. MembershipsService дополнительно вставлял такую же проекцию. На реальной базе вторая вставка вызывала Prisma P2002 и откат всей транзакции. Повторялись все ошибки P2002, включая этот постоянный конфликт, после чего API возвращал 500. Mock-тест не моделировал триггер и пропустил дефект.

Повторная вставка удалена. Начисление занятий выполняется существующим триггером в той же транзакции; сервис создаёт только денежную проекцию оплаченного Payment. Суммы Decimal, методы CASH/CARD, категория serviceType=MEMBERSHIP, кассир из JWT, дата-время PAID и привязки к клиенту/услуге/абонементу сохранены и проверены на PostgreSQL. Модель CashTransaction в проекте не используется: каноническая касса работает через Payment/LedgerTransaction.

Повтор P2002 разрешён только для уникального ключа saleRequestId. Остальные конфликты возвращаются как 409; P2003/P2025 сообщают об изменившихся связанных данных, P2021/P2022 возвращают 503 с указанием на необходимость миграций. Необработанные ошибки сохранения возвращают понятный 503 и записываются в серверный лог с event=membership_sale_failed, этапом операции, попыткой, requestId, actorId/clientId, кодом/метаданными Prisma и стеком. Полный DTO не логируется.

Ключ и advisory lock существуют в границах транзакции: при откате запись ключа не сохраняется, блокировка освобождается PostgreSQL. После ответа с details.rollbackConfirmed=true frontend сохраняет значения, разблокирует поля и создаёт новый ключ при следующей отправке. При неизвестном результате (потеря сети/неопределённый 5xx) исходный ключ сохраняется, чтобы повтор не провёл оплату дважды. Generic Internal server error заменён понятным русским текстом.
