# Модули клуба и права ролей

Настройки → «Модули и права доступа», только ADMIN. Карточки управляют доступностью пяти разделов для всего клуба; матрица — доступом ADMIN, MANAGER, TRAINER и STABLE_WORKER. Изменение подтверждается перед записью. Отключение сохраняет данные и закрывает модуль даже администратору. ADMIN всегда FULL: это проверяют сервис и ограничение CHECK в PostgreSQL.

Модель предназначена для существующего развертывания с одной базой на клуб: в проекте нет tenant/club ID. Уникальны module и пара role/module. Для общей базы нескольких клубов потребуется добавить clubId во все ключи, запросы и контекст авторизации.

Дефолты: ADMIN/MANAGER — FULL; TRAINER — SCHEDULE FULL, STABLES/VETERINARY READ_ONLY, остальные HIDDEN; STABLE_WORKER — STABLES/VETERINARY READ_ONLY, остальные HIDDEN. Миграции заполняют 5 флагов и 20 разрешений, seed идемпотентно дополняет пропуски. Отсутствующие строки получают те же дефолты при чтении. Ошибки БД не заменяются разрешающими дефолтами.

API:

- GET `/api/settings/modules`: глобальные модули и матрица, ADMIN/MANAGER.
- PATCH `/api/settings/modules/toggle`: `{ module, isEnabled }`, ADMIN; boolean без преобразования строк.
- PUT `/api/settings/modules/permissions`: `{ permissions: [{ role, module, accessLevel }] }`, ADMIN; атомарное обновление переданных ячеек, до 20 записей; дубликаты и понижение ADMIN запрещены.
- GET `/api/settings/my-permissions`: `{ role, modules: [{ module, isEnabled, accessLevel }] }`, любая авторизованная роль.
- GET `/api/payroll/me?from=YYYY-MM-DD&to=YYYY-MM-DD`: свои начисления TRAINER/STABLE_WORKER при включенном STAFF_PAYROLL. staffId проверяется относительно текущего пользователя; чужие данные запрещены.

`@RequireModule(module, minAccessLevel = READ_ONLY)` и ModuleAccessGuard работают после JWT. HIDDEN запрещает все запросы; READ_ONLY разрешает GET/HEAD/OPTIONS и запрещает остальные методы, включая PUT. Явный минимум FULL запрещает также GET при READ_ONLY. Глобальный флаг проверяется до прав роли. Защищены занятия, бронирования, загрузка лошадей, денники, договоры/услуги постоя, оба ветеринарных API, журнал здоровья, оплаты/расходы, персонал и зарплата. Вложенные данные скрытых модулей и ставки фильтруются общим SanitizeRbacInterceptor.

Матрица задает доступ к разделу вместе с существующими ограничениями операций: FULL не отменяет проверку своих занятий, управление кассой, выплаты или ограничения удаления. Ранее настроенные RoleAccess тоже сохраняются и применяются вместе с матрицей. Расширение прав раздела само по себе не расширяет разрешенные бизнес-операции.

PermissionsProvider загружает общий снимок для текущей роли, повторяет чтение при фокусе и каждые 30 секунд; локальное сохранение обновляет снимок сразу. Меню скрывает недоступные разделы, ModuleGuard защищает прямые URL и формы new/edit, действия учитывают canWrite. Сетевая ошибка закрывает доступ с кнопкой повтора. Сервер проверяет актуальные настройки на каждом запросе без кеша.

Проверка: `npm --prefix backend run test`, `npm --prefix frontend run test`, `npm --prefix frontend run lint`, обе сборки. Mock Playwright: `module-access.spec.ts` (desktop/mobile, клавиатура, ошибка и повтор). Реальная БД и браузер: после сборки обоих приложений `DATABASE_URL=<локальная PostgreSQL> node backend/test/run-modules-postgres.cjs`. Runner создает временную схему, применяет все миграции, проверяет дефолты и CHECK ADMIN, запускает приложение с изолированной тестовой учетной записью и выполняет `modules.live.spec.ts`, затем удаляет только свою схему.

Для установки применить `prisma migrate deploy` из backend и перезапустить backend. Генерация клиента — `prisma generate`; при блокировке DLL на Windows остановить использующий Prisma процесс перед генерацией. Миграции роли и настроек разделены, чтобы новое значение PostgreSQL enum было зафиксировано до заполнения таблицы разрешений.
