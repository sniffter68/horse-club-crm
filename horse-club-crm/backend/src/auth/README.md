# Авторизация

`AuthModule` подключён в `AppModule`. Установлены зависимости NestJS, Passport,
JWT, bcrypt и типы TypeScript; версии закреплены в `package-lock.json`.

## Контракт Prisma

Код использует `@prisma/client` (Prisma 6, стандартный генератор `prisma-client-js`).
В доступной рабочей папке исходная схема отсутствует. Для сборки требуется
сгенерированный клиент с моделью `User`: `id` (String или Int), уникальным `email`,
`passwordHash`, `role`, и enum `Role` со значениями ADMIN, MANAGER, TRAINER.
Остальные обязательные поля модели должны иметь значения по умолчанию либо
должны быть добавлены в DTO и операцию создания после восстановления схемы.

## Запуск

Перед запуском передайте `JWT_SECRET` через окружение: случайный секрет не менее
32 байт. Например, секрет можно сгенерировать командой
`node -e "console.log(require('node:crypto').randomBytes(48).toString('base64'))"`.
Не храните рабочий секрет в репозитории. `.env.example` содержит только шаблон;
приложение самостоятельно `.env` не загружает. Используйте окружение контейнера
или `node --env-file=.env dist/main.js`.

`npm run typecheck` проверяет типы, `npm run build` собирает приложение,
`npm start` запускает его. Сборка требует восстановленной схемы и генерации
Prisma Client. Первый ADMIN должен быть создан доверенным seed-процессом.

## HTTP

- `POST /api/auth/login`: `{ "email": "...", "password": "..." }`;
  ответ `{ "access_token": "..." }`, неверные учётные данные — HTTP 401.
- `POST /api/auth/register`: `{ "email": "...", "password": "...", "role": "TRAINER" }`;
  доступ только ADMIN с Bearer JWT; возвращаются только `id`, `email`, `role`.
  Пароль — минимум 12 символов, максимум 72 UTF-8 байта.
- `GET /api/auth/me`: текущие `id`, `email`, `role`; требуется Bearer JWT.

Для защиты контроллера подключите `AuthModule` в его модуль и используйте
`@UseGuards(JwtAuthGuard, RolesGuard)` вместе с `@Roles(Role.ADMIN, Role.MANAGER)`.
`@CurrentUser() user: AuthUser` получает пользователя из проверенного токена.
Один `@Roles()` без гардов не включает авторизацию.

Access JWT подписывается HS256, содержит `sub`, `email`, `role`, `authVersion`, `iat`, `exp` и действует
30 дней. JwtStrategy проверяет пользователя, актуальную роль и tokenVersion в БД.
Изменение роли/пароля и Logout отзывают ранее выданные токены.
`.addBearerAuth()` документирует схему, проверку выполняет `JwtAuthGuard`; браузер использует HttpOnly cookie.

## Проверки

`npm run test:unit` транспилирует код без проверки типов и запускает шесть тестов
с подменой границы Prisma, поскольку исходная схема недоступна. Тесты используют
настоящие bcrypt, JWT/Passport, ValidationPipe и RolesGuard. Это отдельная проверка
поведения, которая не заменяет `npm run typecheck` и интеграционные тесты с PostgreSQL.

JWT authVersion содержит строковое значение User.tokenVersion. Обновления профиля/VK не меняют версию.
Logout увеличивает tokenVersion. Триггер БД увеличивает её при изменении passwordHash или role.
При первом развёртывании миграции старые JWT с authVersion=updatedAt потребуют повторного входа.


## Постоянная браузерная сессия (2026-10-21)

Access JWT и HttpOnly cookie действуют 30 дней. `POST /api/auth/refresh` использует отдельную HttpOnly refresh-cookie, возвращает только маркер `cookie-session` и заново устанавливает обе cookie. SameSite=Strict, Secure в production, Path=/, префикс __Host-; CSRF-проверка Origin учитывает обе cookie. Настоящие JWT не передаются JavaScript и не хранятся в localStorage.

По требованию владельца серверного тайм-аута бездействия нет: refresh JWT не имеет exp, проверяется подпись HS256, тип refresh, существование пользователя, роль и tokenVersion. Этот JWT не принимается как access-токен. Cookie хранится 400 дней с продлением при refresh; очистка данных сайта, приватный режим и ограничения браузера могут потребовать нового входа. Logout увеличивает tokenVersion и удаляет обе cookie; смена роли/пароля по-прежнему отзывает доступ.

Клиент повторяет запрос после 401 один раз, объединяя одновременные refresh. Ошибка refresh сохраняет экран и локальный маркер сессии и показывается как ошибка запроса; сервер продолжает запрещать доступ. Автоматической очистки сессии/редиректа по 401 нет. Явный выход использует тот же механизм обновления перед отзывом сессии. При недоступном сервере выход сообщает, что отзыв не подтверждён.

Развёртывать backend и frontend вместе. Миграция Prisma не требуется. Сессии, созданные до этого изменения, не имеют refresh-cookie: для перехода на новый режим нужен один повторный вход. Секрет JWT_SECRET должен сохраняться между перезапусками.
