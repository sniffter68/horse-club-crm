# Лиды и VK Callback

`POST /api/leads` публичный. Тело: `firstName`, `phone` (международный формат E.164, например `+79991234567`), необязательные `email`, `serviceId` (UUID), `preferences`. Ответ 201: `{ success: true, clientId, message: "Заявка успешно принята" }`. Ошибки валидации — 400, неизвестная услуга — 404.

Поиск клиента выполняется по уникальному телефону. Для существующего клиента заполняются только отсутствующие имя/email/preferences, чтобы публичная форма не заменяла сохранённые персональные данные. Для нового клиента `isRider=true`. Контактные номера, уже хранящиеся в CRM, должны использовать тот же формат; миграция не нормализует и не объединяет исторические записи автоматически.

Заявка на услугу сохраняется в `LeadRequest`: это черновик без времени, тренера и лошади. `Booking` по-прежнему требует существующее занятие. Уникальная пара клиент/услуга предотвращает дубли черновиков. Создание клиента и черновика выполняется одной serializable-транзакцией с ограниченными повторами при конкуренции. Перевод черновика в занятие — следующий этап интеграции.

## Схема

Миграция `prisma/migrations/20260908040000_leads_vk/migration.sql` добавляет уникальность `Client.phone`, уникальный nullable `Client.vkUserId` типа BigInt и `LeadRequest`. При дублях телефона миграция останавливается, не объединяя клиентов. BigInt в HTTP JSON сериализуется строкой, включая вложенные данные занятий.

В текущей dev-базе, ранее созданной через `db push`, SQL применён через `prisma db execute`; это не записывает миграцию в `_prisma_migrations`. Перед использованием `migrate deploy` для этой базы нужно согласовать историю миграций. В новой базе с корректной историей используется обычный `prisma migrate deploy`, затем `prisma generate`.

## VK

В `backend/.env` предусмотрены пустые переменные:

```env
VK_BOT_TOKEN=
VK_CONFIRMATION_CODE=
VK_SECRET_KEY=
VK_GROUP_ID=
```

Заполните токен сообщества, код подтверждения Callback API, секрет и положительный числовой ID сообщества. Перезапустите backend. Зарегистрируйте публичный HTTPS URL `/api/vk/callback` в настройках сообщества, включите `message_new` и сообщения сообщества.

Секрет принимается из тела `secret` либо заголовка `x-vk-secret` / `secret`. Проверяются секрет и `group_id`, в том числе для confirmation. Ответ confirmation — код как text/plain; обработанные и неизвестные события получают `ok`. При отсутствии конфигурации — 503, при неверном секрете/группе — 403. Без токена основной CRM запускается; получение сообщений ботом недоступно.

Личные входящие сообщения ищут клиента и тренера по `BigInt(from_id)`. Беседы и исходящие сообщения игнорируются. Для ответов используется vk-io, стабильный `random_id` на событие для повторной доставки. Ошибка отправки возвращает 503; секреты и детали SDK-запроса не выводятся. Реальная отправка в VK требует заполненной конфигурации и отдельно проверяется в сообществе.

## Прикладные диалоги

У VK/vk-io нет Telegram-кнопки `request_contact`. Используются поддерживаемые текстовые кнопки и подтверждение одноразовым кодом. Знание номера не даёт доступа к профилю или списаниям.

1. ADMIN/MANAGER вызывает защищённый `POST /api/vk/link-codes` с `{ "kind": "CLIENT" | "TRAINER", "id": "UUID записи" }` и передаёт код владельцу по проверенному каналу связи. Endpoint возвращает код, срок действия и готовую команду. Кнопки выдачи кода в CRM пока нет; доступен API.
2. Пользователь отправляет `привязать +79991234567 КОД`. Номер нормализуется через libphonenumber-js (национальный формат по умолчанию RU). В транзакции проверяется код, соответствие телефона выбранной записи и отсутствие чужой привязки. Сохраняется `vkUserId`. Код действителен 15 минут, хранится как SHA-256 и не может быть использован другим VK-пользователем.
3. Новый посетитель может выбрать «Первичная заявка» и отправить `заявка Имя; +79991234567`. Используется LeadsService, новый клиент получает `isLead=true`. Привязка существующей записи по одному номеру не выполняется.

Меню клиента: «Баланс абонемента» и «Мои тренировки». Баланс выбирается строго по `Membership.clientId`, сроку и положительному остатку. Миграция `20260908050000_vk_scenarios` заполняет владельцев старых абонементов только при однозначной связи с одним клиентом. Абонементы без однозначного владельца нужно связать вручную; новые абонементы следует создавать с `clientId`. Выдача результата — страницами по 10 записей.

Меню тренера: «Расписание на сегодня», в часовом поясе `CLUB_TIME_ZONE`. Показываются занятия, включая занятия без участников; для каждого участника — inline-кнопки. В настройках VK Callback нужно дополнительно включить `message_event`. Кнопки обрабатываются через `sendMessageEventAnswer`.

Отметки записываются в `Booking.attendanceStatus`: `PENDING`, `ATTENDED`, `NO_SHOW`. Это статусы конкретного участника; они не меняют статус всей групповой тренировки. `MembershipLedgerService.markAttendance` проверяет назначенного тренера, начало занятия и отсутствие отмены внутри serializable-транзакции. Посещение и неявка списывают занятие через существующий журнал, повтор не списывает второй раз. Бронирования без абонемента меняют только отметку. Запрос PostgreSQL advisory-lock приведён к text, чтобы Prisma не пыталась десериализовать void.

Для уведомлений установите `VK_ADMIN_PEER_ID` — положительный ID администратора либо peer_id беседы (2000000000 + номер беседы). В транзакции лида создаётся `VkNotification`; повтор одной заявки клиент/услуга не создаёт дубль. Worker каждые 10 секунд отправляет до 20 уведомлений и отмечает доставку. При сбое запись остаётся для повтора, `random_id` стабилен. При пустом токене отправка отключена, при пустом peer_id уведомления не создаются. Адресата нужно заранее добавить в беседу/разрешить сообщения сообщества.

Дополнительные тесты: `test/vk-bot-scenarios.test.cjs`; проверка настоящего списания и привязки на PostgreSQL — `node --env-file=.env --test test/vk-bot-scenarios.live.cjs` после сборки. VK в тестах подменяется, настоящие сообщения не отправляются.

## Проверки

`npm run typecheck` и `npm test`: HTTP-контроллеры тестируются через Supertest с подменой Prisma/VK; проверяются валидация, публичность лидов, дубли, confirmation, секрет, группа и маршрутизация. `node --env-file=.env --test test/leads.live.cjs` после сборки проверяет реальные параллельные заявки на PostgreSQL и удаляет собственные тестовые записи.
